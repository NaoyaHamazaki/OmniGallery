# UGC 作品出品機能 — 要件と対応方針

- ステータス: 検討メモ (未着手)
- 作成日: 2026-11-13
- 対象: OmniGallery PoC (FastAPI + Godot 4.7 Web / Railway)

ユーザーが自分の作品 (2D 画像 / 3D モデル) を出品し、管理者の承認後に館内へ展示される仕組みを追加する。
当面はクローズドな UAT (受け入れテスト) として、ログインなしでもアップロードできる状態から始める。

---

## 1. 全体の流れ

```
[館内] 出品受付の案内 ──クリック──▶ モーダル (説明 + 「出品ページへ」ボタン)
                                         │ 別タブで開く
                                         ▼
[出品サイト /submit]  ① ログイン/新規登録の案内 (UAT 中はスキップ可)
                      ② 受付トップ: 2D / 3D を選択
                      ③ アップロード: ファイル選択 → 適合性チェック → OK なら「次へ」が有効
                      ④ 作品情報の入力 → 入力チェック
                      ④' 展示場所の希望 (一般公開ルーム / プライベートルーム、フロア、見せ方)
                      ⑤ 確認
                      ⑥ 完了 (「審査をお待ちください」)
                                         │
                                         ▼
[管理画面 /admin]     ⑦ 審査 (内容確認 → 承認 / 差し戻し / 却下)
                      ⑧ 承認時に配置場所を決定 (空きがなければ増築 = 階を追加)
                                         │
                                         ▼
                      ⑨ 展示開始 + 出品者へ「展示されました」メール (Resend)
```

---

## 2. 現在の仕様との関係 (流用できるもの / 変更が必要なもの)

| 項目 | 現状 | 出品機能に向けて |
|---|---|---|
| 作品データ | SQLite `artworks` テーブル。`status` 列 (既定 `published`) あり | `status` を `pending` / `approved` / `rejected` / `published` に拡張。出品者・審査情報の列を追加 |
| 作品の取得 | `GET /api/artworks` は `status='published'` のみ返す | そのまま流用できる (承認・配置済みのものだけ館内に出る) |
| 配置 | `floor` 列 + クライアント側の固定スロット (`building.get_painting_slots` / `get_pedestal_slots`) | スロットを DB で管理 (`slots` テーブル) し、作品に `slot_id` を割り当てる方式へ |
| 建物 | 2 フロア固定 (`Building.FLOORS = 2`)、レイアウトはコード内の定数 | 階数を API から受け取り、同じ平面の階を積み増せるようにする (2.で後述) |
| 3D 作品 | glb を実行時に読み込み、`display_size` で自動拡縮 | 流用可。アップロード時に容量・ポリゴン数のチェックを追加 |
| 素材の保存先 | `backend/static/` (コンテナ内。再デプロイで消える) | **永続ストレージが必須**。Cloudflare R2 / S3 など (Railway Volume でも可) |
| DB | SQLite (再デプロイで初期化) | **永続化が必須**。Railway PostgreSQL へ移行、または Volume 上の SQLite |
| 館内の UI | モーダル (作品説明・フロアマップ・デバッグ) | 出品受付の案内端末を追加 (ホログラム端末 `HoloKiosk` を流用) |
| 文字 | 館内は英語のみ (Web 版のフォントに日本語なし) | 出品サイトは通常の HTML なので日本語可。館内の作品名に日本語が来るなら日本語フォントの追加が必要 |

## 3. 画面ごとの要件

出品サイトはゲーム (Godot) とは別の通常の Web ページとして作る (フォーム入力・ファイル選択・メール認証はブラウザ標準の部品の方が扱いやすく、スマホでも入力しやすいため)。
FastAPI から配信し、ゲームと同じドメイン (例 `/submit/...`) に置く。

### 3.0 館内の受付案内
- 1F 入口付近に「作品出品受付」の端末を設置 (既存の `HoloKiosk` を流用。色を変えて区別)
- クリックでモーダル: 出品できる作品の種類・審査がある旨・注意事項 + 「出品ページへ」ボタン
- ボタンは別タブで `/submit/` を開く (Web 版は `JavaScriptBridge` で `window.open`)。ゲームの状態は保ったまま

### 3.1 ログイン / 新規登録
- 「作品をアップロードするにはログイン / 新規登録が必要です」と表示
- 新規登録: メールアドレス + パスワード → 確認メール (Resend) のリンクで本登録 → ログイン
- ログイン: メールアドレス + パスワード。パスワード再設定 (メールでリンク送付) も用意
- **UAT モード** (`OMNI_UAT=1`): ログイン不要。「テストモード: ログインなしで出品できます」と表示し、そのまま受付トップへ
- 実装方針
  - パスワードはハッシュ化して保存 (`argon2` または `bcrypt`)
  - セッションは HttpOnly / Secure / SameSite=Lax の Cookie
  - 確認メール・再設定のリンクは期限付きの一回限りのトークン
  - ログイン試行の回数制限 (総当たり対策)
  - 将来の選択肢: 外部の認証サービス (Clerk、Supabase Auth など) やソーシャルログイン

### 3.2 受付トップ (種類の選択)
- 2 列のカード: 「2D 作品 (画像)」「3D 作品 (3D モデル)」
- 各カードに受付形式・上限の要約を表示。スマホでは縦 1 列

### 3.3 アップロード
- 受付形式と上限を明記 (下表)
- ドラッグ & ドロップ / ファイル選択の両方に対応。アップロード中の進捗を表示
- サーバー側で適合性チェックを行い、結果を画面に返す (成功 / 失敗とその理由)
- 成功するまで「次へ」は無効、成功したら有効
- 成功時はプレビューを表示 (2D は画像、3D は簡易ビューア。例: `<model-viewer>` を使えば回転して確認できる)

| 種類 | 受付形式 | 上限の案 | サーバー側のチェック |
|---|---|---|---|
| 2D | JPEG / PNG / WebP | 20MB、長辺 8000px 以下 | 実際に画像として開けるか (拡張子ではなく中身で判定)、寸法、EXIF の位置情報は削除。展示用に長辺 2048px 程度へ縮小した版を生成 |
| 3D | glb (glTF バイナリ) | 20MB、5 万ポリゴン以下、テクスチャ 2048px 以下 | glTF として正しいか、ポリゴン数、テクスチャ寸法、アニメーションの有無、外部ファイル参照がないこと。必要なら最適化 (例: gltf-transform でテクスチャ縮小・圧縮) |

- アップロードされたファイルは、承認されるまで非公開の場所に置く (公開 URL を発行しない)
- ウイルス・不正ファイル対策: 中身による形式判定、ファイル名は使わずサーバー側で ID を振る

#### 変換の仕組み (実装済み: `tools/convert_media.py`)
アップロードされたファイルは、この 1 つの入口で受けて「中身 (先頭バイト) で種類を判定 → 展示用に変換」する。投稿 API からはこれを呼ぶだけでよい。

| 種類 | 受け付ける形式 | 展示用の出力 | 処理 |
|---|---|---|---|
| 画像 | JPEG / PNG / WebP / HEIC・HEIF / AVIF / GIF / BMP / TIFF | JPEG (透過ありは PNG) | 向きの補正、長辺 2048px、EXIF (位置情報など) の除去 |
| 動画 | MOV / MP4 / M4V / WebM / MKV / AVI | Ogg Theora + サムネイル | 長辺 960px・30fps・無音、メタデータ除去 (Godot の再生対応は Theora のみ) |
| 3D | glb / gltf / blend / fbx / obj / stl / ply / usd(z) | 軽量版 glb + オリジナル版 glb | Blender で読み込み、材質の整理、静止ポーズの適用、三角形数・テクスチャの削減 |

- 3D は「軽量版を常時表示し、見たい人だけが高品質版を読み込む」二段構え。上限はなくすのではなく、保存容量と悪用対策のための大きめの上限 (例: 200MB) として残す
- 試験で分かった注意点: 外部レンダラー (Octane 等) の材質、色調補正を挟んだテクスチャ、骨組み付きの静止ポーズ、作者のサイン用オブジェクト (板・文字) の混入。いずれも変換で対処済み / 除外オプションあり
- 作者表記が利用条件になっている素材があるため、審査時にクレジットを確認する
- 変換には ffmpeg と Blender が必要。本番では変換用のワーカー (別コンテナ) で実行するのが望ましい (重い処理を API サーバーで行わない)

### 3.4 作品情報の入力
- ログイン中のユーザー情報 (表示名・メール) を初期値として反映。UAT 中はすべて手入力
- 項目 (現在の作品説明モーダルの内容に合わせる)

| 項目 | 必須 | チェック |
|---|---|---|
| タイトル | 必須 | 1〜80 文字 |
| 作者名 (表示名) | 必須 | 1〜60 文字 |
| 制作年 | 任意 | 西暦 4 桁、未来の年は不可 |
| 解説 | 必須 | 1〜1000 文字 |
| クレジット / ライセンス | 任意 | 500 文字以内。権利表記の選択肢 (自作 / CC BY / CC0 など) を用意すると良い |
| 作者の SNS・サイト URL | 任意 | `https://` で始まる URL のみ |
| 連絡用メールアドレス | 必須 (UAT 中) | 形式チェック。展示通知の送り先 |
| 3D の表示サイズ (m) | 3D のみ任意 | 0.3〜3.0。未入力なら自動 |
| 照明の色温度 | 任意 | 「古典的 (電球色)」「現代的 (昼白色)」の 2 択 → `light_kelvin` 3000 / 5000 |
| 権利の確認 | 必須 | 「自分が権利を持つ作品である」「規約に同意する」のチェックボックス |

- エラーは項目ごとに表示。フロントとサーバーの両方でチェック (サーバー側が最終判断)
- 館内のモーダルは BBCode で表示しているため、入力値は既存の `GalleryUI.bb_escape` でエスケープして表示する (現状どおり)

### 3.4b 展示場所の希望 (追加: 2026-11-14)
作品情報の次のページで、展示する部屋と見せ方の希望を聞く。配置と見た目の調整は、この希望をもとにシステムが自動で行う (第 4 章・第 11 章)。

| 項目 | 必須 | 内容 |
|---|---|---|
| 公開範囲 | 必須 | **一般公開ルーム** (誰でも見られる) / **プライベートルーム** (URL を知っている人だけ) |
| 希望フロア / テーマ | 任意 | 一般公開ルームのフロア一覧 (テーマと空きスロット数を表示)。空きのないフロアは選べない。未選択ならおまかせ |
| 展示形式 | 種類で自動 | 画像・動画 = 壁、3D = 台座 (将来: 壁掛けの 3D、床置きの大型作品など) |
| 見せ方の希望 | 任意 | 照明の雰囲気 (暖かい / 自然な白)、大きさ (小 / 中 / 大。3D は高さの目安を表示)、メイン作品の位置を希望するか (一般公開ルームは審査で判断) |

- 空きスロットの数はフォーム表示時に API から取得する。送信時にも再確認し、埋まっていたら選び直してもらう
- 動画は「無音でループ再生」が既定。音声付き再生は将来の選択肢

### 3.5 確認
- 入力内容とプレビューを一覧表示。「戻って修正」「この内容で出品する」

### 3.6 完了
- 「出品を受け付けました。審査完了後に展示され、メールでお知らせします」
- 受付番号を表示。受付確認メールも送る (任意)

### 3.7 管理画面 (審査)
- 管理者のみアクセス可 (UAT 中でも必須)。管理者ログイン、または当面は Basic 認証 + IP 制限
- 審査待ちの一覧 → 詳細 (プレビュー・入力内容・ファイル情報・自動チェック結果)
- 操作: **承認** / **差し戻し** (修正依頼のコメント付き) / **却下** (理由付き)
- 承認時: 配置場所の決定 (第 4 章) → 展示 → 出品者へメール
- 展示中の作品の取り下げ・入れ替えもここから行う
- 操作履歴 (誰がいつ何をしたか) を残す

### 3.8 メール (Resend)
| タイミング | 内容 |
|---|---|
| 新規登録 | メールアドレス確認のリンク |
| パスワード再設定 | 再設定のリンク |
| 出品受付 (任意) | 受付番号と審査の目安 |
| 承認・展示開始 | 展示されたこと、展示フロア、館の URL |
| 差し戻し / 却下 | 理由と、修正して再出品する方法 |

- 送信元ドメインの認証 (SPF / DKIM) を Resend で設定
- API キーは Railway の環境変数 `RESEND_API_KEY` に置き、コードやリポジトリには書かない
- 送信に失敗しても審査処理は止めない (再送できるよう送信ログを残す)

## 4. 配置の決定と増築

### 4.1 考え方
- 展示位置 (スロット) を DB で管理する: `slots` テーブル (階、壁 / 台座、座標、向き、最大サイズ、メイン作品用か)
- 承認時に「空いているスロット」へ作品を割り当てる。2D は壁のスロット、3D は台座のスロット
- 空きがない場合は **増築**: 既存フロアと同じ平面の階を 1 つ上に追加し、そのスロットを `slots` に登録する

### 4.2 Claude による配置の提案
承認ボタンを押したタイミングで、Claude API に配置を提案させる案。

- 入力: 新しい作品の情報 (種類・タイトル・作者・年代・解説・色味など) + 各フロアのテーマ + 空きスロットと周囲の展示作品の一覧
- 出力: 推奨スロット ID と理由 (例: 「2F は印象派中心なので、光の表現が近いこの壁へ」)、空きがなければ「増築して新フロアのテーマ案」
- 管理画面に提案を表示し、**管理者が確定する** (自動で確定しない)。気に入らなければ別のスロットを手で選べる
- 出力は JSON 形式で受け取り、存在しないスロット ID などは検証してはじく
- API が使えない・失敗した場合は、単純なルール (同じ階の空き → なければ次の階 → なければ増築) にフォールバック
- 実装時は、その時点で最新の Claude モデルと公式 SDK を確認して使う

### 4.3 増築 (階を積み増す) ための変更点
| 箇所 | 現状 | 変更 |
|---|---|---|
| 階数 | `Building.FLOORS = 2` (定数) | `/api/config` の `floors` の件数から決める |
| フロア情報 | `floors` テーブル (2 行) | 増築時に行を追加 (名前・テーマ) |
| 建物の生成 | 2 階分の壁・床・屋根 | 階数ぶん繰り返して生成 (階高 5.5m)。屋根は最上階の上に |
| 縦の移動 | 階段・エスカレーターは 1F⇔2F の 1 組 | 階ごとに同じ位置へ積み重ねる。エレベーターの行き先ボタンは階数ぶん |
| 外観 | 正面の高さは 2 階分で固定 | 階数に合わせて外壁・コーニスの高さを変える |
| 読み込み | 1F → 2F の順に固定 | 入館時は 1F だけ、他の階は移動時に読み込む (今の「移動中に準備」の仕組みを階数分に拡張) |
| フロアマップ | 2 フロアを左右に並べて表示 | 階数に応じてタブ切り替えなどに変更 |

## 5. データ設計の案

```
users        id, email (一意), password_hash, display_name, email_verified_at, role (user/admin), created_at
submissions  id, user_id (UAT 中は NULL 可), kind (painting/model), status (pending/approved/rejected/withdrawn),
             title, artist, year, description, credit, link_url, contact_email, display_size, light_kelvin,
             file_key (保存先のキー), preview_key, file_meta (寸法・容量・ポリゴン数などの JSON),
             review_comment, reviewed_by, reviewed_at, created_at
slots        id, floor, kind (wall/pedestal), x, y, z, normal / facing, max_w, max_h, featured
artworks     既存 + submission_id, slot_id (配置先), published_at
mail_logs    id, to, template, status, error, created_at
```

- 承認時に `submissions` → `artworks` (status=`published`, `slot_id` 付き) を作成
- 館内のクライアントは `slot_id` の座標を使って配置する (今のクライアント側固定スロットから移行)

## 6. API の案

| メソッド | パス | 用途 |
|---|---|---|
| POST | `/api/auth/register` / `/api/auth/login` / `/api/auth/logout` | 新規登録・ログイン・ログアウト |
| POST | `/api/auth/verify` / `/api/auth/reset` | メール確認・パスワード再設定 |
| POST | `/api/uploads` | ファイルのアップロード + 適合性チェック (結果を返す) |
| POST | `/api/submissions` | 作品情報を付けて出品 |
| GET | `/api/submissions/mine` | 自分の出品状況 |
| GET | `/api/admin/submissions?status=pending` | 審査待ち一覧 (管理者) |
| POST | `/api/admin/submissions/{id}/approve` | 承認 (配置スロット or 増築を指定) |
| POST | `/api/admin/submissions/{id}/reject` | 差し戻し / 却下 |
| POST | `/api/admin/placement/suggest` | Claude による配置提案 |

## 7. インフラ・運用の前提

- **永続化が必須**: 現在は DB も素材もコンテナ内にあり、再デプロイで消える
  - DB: Railway PostgreSQL (推奨) または Volume 上の SQLite
  - ファイル: Cloudflare R2 / S3 (推奨) または Railway Volume。公開は承認後のみ
- 環境変数: `OMNI_UAT`, `RESEND_API_KEY`, `ANTHROPIC_API_KEY`, `ADMIN_*`, `DATABASE_URL`, ストレージの認証情報
- 現在の CORS は全許可 (`*`)。出品・ログインを入れる段階で配信ドメインに絞る
- 不正対策: アップロードの回数制限、容量上限、通報ボタン (要件定義書の「モデレーション」)

## 8. UAT モードと本番の違い

| 項目 | UAT (`OMNI_UAT=1`) | 本番 |
|---|---|---|
| 出品者のログイン | 不要 (連絡先メールは入力必須) | 必須 |
| 管理画面 | 必須 (Basic 認証 + IP 制限でも可) | 管理者ログイン必須 |
| 公開範囲 | 関係者のみ (URL を限定共有) | 一般公開 |
| メール | 実送信 (テスト用ドメインでも可) | 実送信 |

## 9. 未決事項

- 2D 作品の額・展示サイズを出品者が選べるようにするか
- 1 人あたりの出品数・展示期間の上限 (入れ替え制にするか)
- 却下理由の定型文
- 日本語の作品名・解説を館内で表示するための日本語フォント (容量が増えるのでサブセット化を検討)
- 管理者を複数にするか、承認に 2 人以上の確認を必要とするか
- 増築の上限 (階が増えすぎた場合の扱い。テーマ別の別館にする案も)

## 11. 展示ルームとスロット (追加: 2026-11-14)

### 11.1 部屋の種類
| 部屋 | 公開範囲 | 配置のしかた | 審査 |
|---|---|---|---|
| 一般公開ルーム | 誰でも (美術館の通常のフロア) | フロアごとに決めた空きスロットへ配置。テーマ・メイン作品は運営が管理 | 必須 |
| プライベートルーム | ルームコードを知っている人だけ | 出品者ごとの小部屋 (定型レイアウト)。出品者が自分の作品だけを並べる | AI による自動審査 (11.4) |

#### プライベートルームへの入り方 (確定)
1. 館内のエレベーターのかご内に「PRIVATE」ボタンを追加
2. 押すとモーダルが開き、ルームコードの入力欄を表示 (スマホでも入力しやすい大きめの入力欄 + 数字/英字キー)
3. 正しいコードなら、ドアが閉まって移動演出 → その人のプライベートルーム (館内とは別マップ。タイムアタックのコースと同じ方式) に到着
4. 部屋から出るときはエレベーターで元のフロアへ戻る

- **ルームコード**: 出品者のルーム作成時に発行 (例: 英数字 8 桁、紛らわしい文字 0/O・1/I を除く)。出品者は投稿サイトのマイページで確認・再発行 (再発行で古いコードは無効) できる
- **総当たり対策**: コード照合はサーバー側。端末 / IP ごとの試行回数制限 (例: 10 回 / 10 分)、失敗時は一定時間待たせる
- **作品ファイルの保護**: プライベートルームの作品は公開 URL を発行しない。コード照合に成功したセッションにだけ、期限付きの URL を返す
- 定型レイアウト: 小 (壁 6 + 台座 2) から始め、作品が増えたら中・大のレイアウトへ

### 11.4 審査 (一般公開ルームとプライベートルームの違い)
| | 一般公開ルーム | プライベートルーム |
|---|---|---|
| 審査 | AI の一次判定 + **管理者の承認** | **AI の判定のみ** (問題なければ自動で展示) |
| ブロック対象 | 公序良俗に反するもの (性的・暴力的・差別的表現など)、他者の権利侵害が明らかなもの (有名キャラクター・ロゴ・他人の作品の無断転載など) | 公序良俗に反するもの (同左)。権利面は利用規約で出品者の責任とし、通報があれば管理者が確認 |
| 判定がグレーのとき | 管理者の判断 | 保留にして管理者へ回す (自動では展示しない) |

- AI 判定は Claude API (画像はそのまま、動画はサムネイルと数枚のフレーム、3D はレンダリングした数方向の画像を渡す) で行い、判定結果 (OK / NG / 要確認) と理由を `submissions` に保存する
- NG の場合は出品者に理由を通知 (メール)。誤判定に備えて「再審査を依頼」ボタンを用意
- 展示後も通報ボタン (要件定義書のモデレーション) から管理者に届くようにする

#### 現状のファイルでの例
- 今回お試しで展示したアイアンマンの像は、一般公開ルームでは「他者の権利 (キャラクター)」でブロック対象。プライベートルームなら公序良俗の面では問題なく展示可 (権利は出品者の責任)

### 11.2 スロットの管理
- スロットは DB (`slots` テーブル) で管理し、部屋 (`room_id`) とフロアに属する
- フロアごとに「投稿作品用に開放するスロット」を定める (運営が選んだ作品用の枠と分ける)。開放数はフロアの設定値で管理
- 一般公開ルームで空きがなくなったら、第 4 章の増築 (階の追加) で枠を増やす

```
rooms   id, kind (public/private), owner_user_id, name, layout (small/medium/large), share_token, created_at
slots   id, room_id, floor, kind (wall/pedestal), x, y, z, facing, max_w, max_h, featured, open_for_ugc
```

### 11.3 配置と見た目の自動調整
- 承認時に、出品者の希望 (3.4b) → 空きスロットの順で割り当てる。一般公開ルームは Claude の提案 (4.2) を管理者が確定、プライベートルームは出品者の部屋に自動配置
- 見た目は自動で調整 (出品者の希望は反映する):
  - 額 / 台座の大きさ: 画像の縦横比、3D の大きさの希望 (小・中・大) から算出し、スロットの最大サイズに収める
  - 照明: 希望の雰囲気 → 色温度 (暖かい = 3000K / 自然な白 = 5000K)。角度・範囲は作品サイズから自動
  - 3D: 静止ポーズの適用、金属感の調整、柵とキャプション台の自動設置 (実装済み)
  - 動画: 無音ループ・画面風の発光 (実装済み)

## 10. 対応の順番 (案)

1. 永続化 (PostgreSQL + オブジェクトストレージ) と `status` の拡張
2. 出品サイト (UAT モード: ログインなし) — 受付トップ → アップロード → 入力 → 確認 → 完了
3. 管理画面 (審査・承認・却下) + 承認メール (Resend)
4. スロットの DB 管理と、クライアントの配置方式の移行
5. 館内の出品受付端末
6. Claude による配置提案
7. 増築 (階数の可変化)
8. 本番向け: ログイン / 新規登録、CORS の制限、回数制限、通報
